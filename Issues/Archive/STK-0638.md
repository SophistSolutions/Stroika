## Description

WebServer ConnectionManager (and Connection) handling restructure - so while reading headers, only one thread used.
Basically, the issue is an attack - where you send one byte of http request, and hangup webserver - so one thread allocated to each thread in pool.
But this also makes a big differnece in conneciton wtih connection keepalives. We must split the handling process as:
>> one thread (or maybe one pool) which waits on all open connection sockets which are in the state of reading headers. and then for them to select on the input and read as available just until headers parsed.
>> THen move state of connection to body/handle, and then assign one connection thread task to that thread pool.
and when that response is done - even if the thread still exists - top thread handling, and send back to state of read headers and that process above.

Outline of IMPL strategy:
> Fix messageheaderstreamscanner - to allow reset back to start (seek) on start parsing message, but cache upstream data read so far. (maybe already like this)
> Then fix ReadHeaders to only assign this wrapper once (first time through starting at a point)
> Fix Readheaders to ABORT (and reset to start) the messagehaderstreamscanner if not enough data available (so non-blocking reads)
> Maintain list of waiting-for-data sockets, and do select (epoll) on them - looikng for new data.
Ones with new data - try the ReadHeaders on again, and when ReadHeaders works, process the command in a thread, and otherwise reset it again, and wait some more
Each of these ReadHeader calls can be in a task thread.
Then - we NEVER do blocking reads in ReadHeader - inside a threadpool task. You STILL can kill this process (hangup) by requireming body data nd having that block (thoghh I could also fix that by requiring read at head for content length). Not needed on first pass. I THINK this can be done in a few hours, but hard to test.
