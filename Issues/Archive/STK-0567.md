## Description

Add some way to tell if a Read () call would be blocking on a stream, or to see if input is available, or to make a non-blocking read call.
Not SURE this is a good idea. It must be done in such a way that it doesnt make Streams harder to use (writing backend stream rep). Not sure of exactyly the right definition, but experimenting.

### Lewis Pringle - 2023-12-29T00:21:31.432-0500

Considering alternatives, because this is complicated.

ALT A:
in some subclasses (that would actually block) - like socketstream - have CTOR MODE (or Ptr settable mode) - where we translate ‘EWOULDBLOCK’ to a new Streams exception EWouldBlockStream. Could work on READS and WRITES. COMPLETLY transparent. No need for (much support anywhere) - no additional streams rep methods at least.
Would need to be careful, for example, in a Character decode reading bytes, it might make several calls to the underlying byte stream, the first succeeded, getting a partial cahracter, and the second failing with EWOULDBLCOK. Must buffer up the partial cahracters in any intervening calls (probably easy and proabbkly already done that way). And just allow for pass through - if we get an exception - WOULDBLCOK (or even TIMEOUT on read etc) - just pass trhough.
ALT B:
| Just have ‘data avaialbale’ method. FOr most streams classes, a very simple pass through. Trouble is - for some - its not. Like for that aforementioned character reader, if I read tehre is a byte avaiable - but dont know which, I dont know how many charaacters for ME to return.
ALT C:
| What I have now - with ReadNonBlocking.

NOTE - with Alt A:
| I can impelment the same PTR API I have now - just doing a regular READ, and if I get that excpetion - return nullopt.
UPSIDE of plan a:
I THINK Streams API becomes significantly simpler, as we lsoe complex ReadNonBlockINg API
Mechanism used for readnonblcokging now also works for WRITENONBLCOKGIN
DOWNSIDES
| Must impliement new blocking API ina couple classes - Probably SharedStream, and SocketStream (thouse could be it - maybe even have a TIMEOUT feature - not just a flag for not to block).
Must review all the code in between to make sure its ‘friendly' about thiese ewouldblcok excpetions (porbably easy).
Performance hit in the ewouldblcok situation. Not sure I care much since sb quite rare and intrinnsically expensive situation anyhow. But its a possible issue.

https://stackoverflow.com/questions/4058368/what-does-eagain-mean

ALT D
SIMILAR to A, but instead of setting flag/timeout in SocketStream and/or SharedStream, set a thread_local variable inside of InputStream::ReadNonBlocking.
THIS would mean no special API to do setup in blockign streams - they just check a flag (thread local) about input streams or output streams. This flag would be set magically in ReadNonBlocking. This has implication for using stremas with coroutines (which I haven’t tried/thought out). MAYBE the most serious problem iwth this idea. But even that might be tracktabl (just need a way to capture aggregation dependency map).
Somehat simpler setup than plan A, and you avoid possible bug of someone calling ReadNonBlocking without having setup any streams to throuw the rihgt exctions. Leaning towards D.
