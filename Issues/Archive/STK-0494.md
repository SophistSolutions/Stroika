## Description

This MAY be the reason for the subtle memory bugs on the ARM BLKQCL device.
I've seen some (vague - I dont understand) indications that x86 has memory strongly 
ordered and arm - maybe - not.
That could explain why I havent seen the valgrind or memory corruptions issues on x86.
Or it could be soemthing else.
http://www.boost.org/doc/libs/1_54_0/doc/html/atomic/usage_examples.html#boost_atomic.usage_examples.example_spinlock says to use memory_order_acquire.
Unclear wht todo on unlock.
But I THINK the right thing is to use std::memory_order_seq_cst on lock and do nothing on unlock.
At least test that for a bit.

  -  According to http://www.boost.org/doc/libs/1_54_0/doc/html/atomic/usage_examples.html#boost_atomic.usage_examples.example_spinlock
  -  it makes sense to use memory_order_acquire, but that doesn't seem right, as the
  -  lock could protect reading or writing another memory area.
But thats wrong.
You use a mutex to protect some datastrucutre. When a thread acquires the lock, it wants to make sure its copy is up to date (this acqure). ANd when its done - releases the lock - it wants to assure its changes are published (the release).
This has PROBABLY been fine since 2.0a156 - but is now 99% sure fine as of Stroika v2.0a228 (and closing issue)
